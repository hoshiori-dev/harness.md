# HARNESS.md 格式规范

版本：`alpha`

`HARNESS.md` 记录一个项目的 Agent harness 设计：编码 Agent 在哪里运行，读什么，
怎样检查自己的工作，什么会拦住一次错误的改动，哪些事它可以不问就做。本文定义这个
文件的格式。本文是英文规范 `spec.md` 的中文翻译；两者不一致时，以英文为准。

## 1. HARNESS.md 是什么

项目的 harness 该怎样设计，以 `HARNESS.md` 为唯一依据。它对 harness 的作用，相当于
`DESIGN.md` 对视觉设计的作用：说明 harness 应该是什么样，理由是什么。入口文件
（`AGENTS.md` 或同类文件）、知识文件、权限文件、Hook、检查和 CI 配置，都是这份
设计的实现。

### 1.1 两种用法

怎么用由使用者决定，格式不偏向其中一种。

- **当作模板。** 把一份现成的 `HARNESS.md`（例如来自某个 hub）放进项目根目录，
  告诉编码 Agent 这个项目要做什么，由 Agent 把它展开成完整的 harness。建成之后
  这份文件可以删除。
- **当作锚定文档。** 文件留在仓库里，很少改动，像一份章程。只有在检查 harness
  是否漂移或有意改进 harness 时，才去读这份文件、改这份文件。

从别处拿来的 `HARNESS.md`，Context 一节写的是别人的项目。要把它留作自己项目的
锚定文档，先把这一节改写成自己项目的情况；哪些章节的理由建立在原来的背景上，
也要逐一重新考虑。

### 1.2 很少加载，没有长度限制

Agent 平时不必加载 `HARNESS.md`。它不是入口文件，日常任务用不到它。只有三种
情况需要按需打开：创建 harness，检查 harness 是否漂移，改进 harness。

它不常驻 Agent 的上下文，所以没有长度限制。入口文件和 skill 则不同：入口文件
每个任务都要加载，skill 每次触发都要加载，其中每一行都在反复占用上下文。这份
文件打开之前不占上下文，该写多长就写多长，写到读者单凭这一份文件就能把 harness
建出来为止。

### 1.3 以谁为准

把文件留作锚定文档时：

- **设计意图以 `HARNESS.md` 为准。** 产物指实现这份设计的任何文件。产物与
  `HARNESS.md` 不一致时，错的是产物，除非先改了 `HARNESS.md`：要么修产物，
  要么修订文件。
- **事实以代码为准。** 一条命令实际做什么、一个路径是否存在，由代码和配置回答。

## 2. 目标与原则

这个格式只有一个目标：**写一份 `HARNESS.md` 需要本规范，读懂一份 `HARNESS.md`
不需要。**

作者（人或 Agent）照着规范写，得到的文件结构可以预期。读者（人或 Agent）即使
从没见过本规范，也没有安装任何 skill 或工具，仍然能读懂文件在说什么。

由此得到三条原则。

1. **轻量。** 规范只定义文件的身份字段和章节骨架。轻量的是规范，文件本身可以是
   任意长度。
2. **自由。** 设计本身全部用自然语言书写。规范不限制额外的章节和额外的说明。
3. **自解释。** 文件里的键和取值，读者不用查本规范就能看懂。

## 3. 文件结构

一份 `HARNESS.md` 由两部分组成，和 Agent Skills 的 `SKILL.md` 一样：

1. **YAML frontmatter**，只放文件的身份信息。
2. **Markdown 正文**，放设计本身，按第 5 节的章节骨架组织。

文件是 UTF-8 文本。frontmatter 从第一行开始，这一行只有 `---`，到下一个这样的
行结束。

项目的 `HARNESS.md` 放在仓库根目录。可复用的设计（例如 hub 条目）是同一种文件，
只是不属于任何项目。

## 4. Frontmatter

frontmatter 只说明这份文件是什么，不承载设计内容。凡是关于项目或 harness 的
陈述，都写在正文里。

| 键 | 必填 | 取值 | 含义 |
| --- | --- | --- | --- |
| `name` | 是 | 由小写字母、数字和连字符组成的短名 | 这份设计的名称 |
| `description` | 是 | 字符串 | 这份设计是什么，适合什么样的项目 |
| `version` | 否 | `alpha` | 文件所依据的格式版本 |
| `license` | 否 | 许可证名称，或指向随文件附带的许可证文件 | 这份 `HARNESS.md` 文件本身的许可证 |
| `metadata` | 否 | 任意结构 | 供需要它的平台使用的附加信息 |

`license` 和 `metadata` 沿用 Agent Skills 规范里的同名字段。

规则：

- `name` 和 `description` 必须是非空字符串。`version` 和 `license` 如有，必须是
  字符串。
- 版本按发布先后排序。`alpha` 是第一个版本，目前也是唯一的版本。没有 `version`
  时，校验器按自己支持的最新版本检查这份文件。写了 `version`，就按所写的版本
  检查；所写的版本比校验器支持的最新版本旧时，校验器只附一条提示。校验器不认识
  所写的版本时给出警告，并按最新版本检查。
- 本规范没有定义的顶层键算错误。有信息要写而规范里没有对应的键，就放进
  `metadata`。
- 同一个顶层键出现两次算错误。
- `metadata` 可以是任意结构。格式既不定义也不检查它的内容，格式自己的工具完全
  无视它：不读取，不校验，不比较。哪个平台在里面定义了键，就由哪个平台自己检查。
  例如官方 hub
  把 `tags` 和 `based-on` 放在 `metadata` 里；那是 hub 的规则，与本格式无关。
- 对 `name` 和 `description` 的限制来自 Agent Skills 规范，但违反它们只给出警告，
  不算错误。`name` 最多 64 个字符，只用小写字母、数字和连字符，不以连字符开头或
  结尾，不出现连续的两个连字符。`description` 最多 1024 个字符。
- Agent Skills 规范还要求 `name` 与文件所在目录同名。本格式不要求：文件放在
  项目根目录时，目录名没有比较的意义。hub 可以在自己的条目规则里要求这一点。

## 5. 正文

### 5.1 章节骨架

规范定义下面这些章节，并按这个顺序排列。其他章节不受限制，可以出现在任何
位置。

| 顺序 | 章节 | 必选 | 它回答的问题 |
| --- | --- | --- | --- |
| 1 | Overview | 是 | harness 为谁服务，要达成什么，不打算管什么，哪些事始终由人来做 |
| 2 | Context | 是 | 设计必须适应、设计者又改变不了的条件，例如改坏的代价、项目要维护多久、谁依赖这里的约定、有没有人盯着 Agent 干活、代码托管平台、harness 面向的客户端与模型 |
| 3 | Invariants | 否 | 每个任务都必须遵守的规则，不论它涉及 harness 的哪一部分 |
| 4 | Style | 否 | 代码本身应该是什么样，Agent 才能在其中工作 |
| 5 | File Structure | 否 | 这份设计要求的目录布局 |
| 6 | Environment | 是 | Agent 在哪里运行，有哪些工具，能碰到什么 |
| 7 | Knowledge | 是 | Agent 怎样了解项目，什么时候读什么 |
| 8 | Feedback | 是 | Agent 靠运行什么、观察什么来验证自己的工作 |
| 9 | Gates | 是 | 哪些确定性检查拦住缺陷 |
| 10 | Authority | 是 | 哪些事 Agent 可以直接做，哪些需要人；它怎样提交、开分支、合并和发布 |
| 11 | Completion | 否 | 动手之前怎样对齐目标，怎样算做完 |
| 12 | Entropy | 否 | 怎样让 harness 与代码保持一致 |
| 13 | Open Questions | 否 | 还没有决定的事 |
| 14 | References | 否 | 这份设计依据的外部资料 |

这个顺序先讲要求，再讲机制，所以必选章节并不都排在前面：

- Overview 和 Context 说明这份设计是什么，理由是什么；
- Invariants、Style 和 File Structure 提出对项目的要求：不可违反的规则，代码
  长什么样，布局；
- Environment 到 Entropy 是 harness 的七层，也就是满足这些要求的机制，按搭建的
  先后排列；
- Open Questions 和 References 收尾。

### 5.2 怎样认定一个章节

- 规范定义的章节是二级 ATX 标题（`## Overview`），标题文字与 5.1 表中的英文名
  完全一致，大小写也一致。正文可以用任何语言书写，但这些标题不翻译。换了文字
  或换了级别的标题不算该章节，围栏代码块里的标题不算标题。一级标题写什么都行。
- 规范定义的章节没有按表中的顺序出现时，校验器给出警告。
- 规范定义的章节出现不止一次算错误。

### 5.3 必选与可选

Environment 到 Entropy 是 harness 的七层。其中五层必选（Environment、
Knowledge、Feedback、Gates、Authority），两层可选（Completion、Entropy）。加上
Overview 和 Context，必选章节一共七个。

这五层必选，是因为 Agent 要工作至少需要这些。Knowledge、Feedback、Gates、
Authority 合起来是最小的一个循环：Agent 了解项目，能判断自己做得对不对，确定性
检查会拦住它的错误，它知道哪些事可以做、在哪里停。Environment 必须和 Authority
放在一起看：不知道 Agent 在哪里运行、能碰到什么，就无法判断该允许它做什么。
五项里缺任何一项，单凭这份文件都建不出能运转的 harness。

必选章节可以写“什么都不做”。项目可以决定某一层不做任何事，但这一节仍然要有，
要把这个决定写出来并给出理由，例如“本项目不设提交前检查，因为它一个季度内就会
丢弃”。这样，决定不做和忘了写就分得清。校验器管不到这一点，因为它从不读正文：
空的章节能通过校验，却帮不了读者。

可选章节不写，表示设计在这一项上没有内容：没有不变量，没有完成标准，等等。
校验器不会为此报告任何东西。

### 5.4 关于个别章节

下面说明各类内容该写进哪一节。至于怎样把一节写到单凭这份文件就能建出 harness，
本规范不管，由帮助作者的工具和 skill 负责。

#### Style

Style 描述代码库自身长什么样。各层都建立在它之上：代码越能说明自己，需要在代码
之外解释的就越少。常见的主题有结构的内聚程度，哪些约束用类型表达而不是靠文字
提醒，命令是否收口到一个入口，测试写到多细，以及项目对新依赖的态度。具体的
格式和命名规则属于格式化工具和 Linter 的配置。

#### File Structure

File Structure 描述这份设计要求的布局：必须有哪些目录和文件，各放什么。它写的
是意图，所以可以列出还不存在的路径，产物应当符合它。可以写成目录树、表格或
一段文字。

#### 仓库里做法不同的部分

同一层在仓库的不同部分做法不同时（例如生产仓库里的 `experiments/` 目录），在
这一层自己的章节里说明。

#### Knowledge 与 References

两节都会列出资料，但读者不同。

- Knowledge 是 harness 的一层，涵盖 Agent 在项目里工作时读的东西：入口文件、
  知识文件，以及工作中应当查阅的外部文档。
- References 说的是这份文件本身。它列出作者写这份设计时依据的外部资料，相当于
  论文末尾的参考文献。Agent 工作时不需要读它们。

判断一份资料放在哪里，就问 Agent 干活时要不要读它。要读，放进 Knowledge；它
只是这份设计的出处，放进 References。

#### 工具

工具写在 Environment。工具指 Agent 在读写文件和执行普通命令之外得到的任何
能力。下面是典型的例子，并未列全：

- 注册到 Agent 客户端的工具和 MCP 服务器；
- 预装在环境里、期望 Agent 使用的命令行程序，例如托管平台的 CLI；
- 项目提供给 Agent 的脚本和任务运行器入口。

Environment 里讲到工具时，通常会写：有哪些工具，各自做什么用；每个工具能碰到什么（只读还是
有副作用，是否触及仓库之外的系统，用哪一份凭证）；什么时候可用；有意不提供哪些
工具。这些都不是必须写的。

工具与相邻几层的分界：

| 问题 | 章节 |
| --- | --- |
| Agent 能用哪些工具，工具能碰到什么？ | Environment |
| Agent 可以用它们做哪些动作，哪些需要人？ | Authority |
| Agent 怎样用工具启动、驱动、观察正在开发的系统？ | Feedback |
| Agent 读什么：skill、知识文件、文档？ | Knowledge |

## 6. 校验

校验器对一份文件没有报告任何错误，这份文件就符合本格式。警告和提示不影响是否
符合。本节列出校验器会报告的全部内容。

**错误**

- frontmatter 缺失，或不是合法的 YAML 映射。
- `name` 或 `description` 缺失、为空，或不是字符串。
- 写了 `version` 或 `license`，但不是字符串。
- 某个顶层键不是本规范定义的。
- 某个顶层键出现两次。
- 缺少必选章节：Overview、Context、Environment、Knowledge、Feedback、Gates、
  Authority。
- 规范定义的章节出现不止一次。

**警告**

- 规范定义的章节顺序不对。
- `name` 超过 64 个字符，或不符合字符规则。
- `description` 超过 1024 个字符。
- `version` 写的是校验器不认识的版本；此时按校验器支持的最新版本检查这份文件。

**提示**

- `version` 写的版本比校验器支持的最新版本旧。

**不检查**

- `metadata` 里的任何内容。
- 额外的章节。
- 任何章节的正文。
