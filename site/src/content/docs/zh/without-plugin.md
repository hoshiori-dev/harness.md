写一份 `HARNESS.md` 要对照规范，读懂一份不用。
所以 [hub](../../hub/) 里的文件，任何编码 Agent 都能用，什么都不必装。

## 把文件交给 Agent，再说明目标

1. 在 hub 里挑一个条目，复制它的地址，或者把文件下载到任意位置。
2. 告诉编码 Agent 这个项目要做什么，并把地址或路径给它。
3. 让它把这份文件当作参考，来设计你项目的 harness。

像下面这样说就够了：

```text
这个项目是一个命令行工具，用来在两块硬盘之间同步照片库。请阅读
<地址> 上的 HARNESS.md 作为参考，和我一起为这个项目设计 Agent harness。
文件里的 Context 一节是为另一类项目写的：先告诉我哪些地方和这个项目
对不上，在创建任何文件之前先给我看计划。
```

最后一句不能省。hub 条目带着原作者的 Context：
改坏的代价有多大，项目要维护多久，有没有人盯着 Agent 干活。
你的项目总会有几处不一样，所以要看哪些决定的理由建立在那份 Context 上，
把它们重新过一遍。

文件不必放进你的仓库，也可以同时给 Agent 不止一份。

## 建完之后：不需要留着文件

harness 建好之后不依赖这份文件。项目不需要有自己的 `HARNESS.md`。

如果想把自己项目的设计写下来，用来分享或者留存，
就让 Agent 写一份描述你现在这套 harness 的 `HARNESS.md`，
而不是保留当初参考的那个条目。

项目也可以决定把这样一份文件留在根目录，作为**锚定文档**：
长期的设计记录，很少改动。Agent 几乎不应该加载它；
检查 harness 有没有漂移或者打算改进 harness 的时候再打开。
产物（实现设计的文件）与锚定文档不一致时，只要文档没有改口，错的就是产物：
要么修产物，要么修订文档。至于事实，比如一条命令实际做什么、一个路径是否存在，
以代码为准。

## 少了什么

不装插件，Agent 靠的是这份文件和它自己的判断。
你少了校验器，少了那些知道每一层怎样设计、怎样建、怎样检查的 skill，
也少了构建之后在干净的上下文里把新文件重读一遍这一步。
对小项目来说，这笔交换往往划算。想手工检查文件格式的话，
[规范](../../spec/)的最后一节列出了校验器会报告的全部内容。
