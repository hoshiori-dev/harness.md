入口是你开始的地方。每个入口都是需要你自己调用的 skill：
即使某句话听起来很像，Agent 也不会自行启动它。
在 Claude Code 里把 skill 当命令输入，例如 `/harness-md:harness-create`；
在 Codex 里写 `$harness-create`；在 Antigravity 里，在请求中写出 skill 的名字。

## 入口怎样和你一起做决定

入口不会先写出一整份设计再让你批准。
它把还没定的决定看成一棵树，定下一个，依赖它的那些才会展开，
然后一轮一轮地处理这棵树。

每一轮，Agent 只看现在已经可以定的决定。
事实由它自己去查：能从仓库里读到的，它从不问你。
证据足以说明某个选项明显更好时，它直接定下来，
并把决定和依据展示给你。
其余的才问你，每个问题都带一个推荐答案和理由。
客户端有提问工具时，问题通过工具给出，你选一项即可；
没有的话，问题合在一条消息里编号列出。

你回答之后，Agent 会展示这一轮的结果：
它定了什么，你答了什么，哪些决定因此展开或者不再需要。
然后它问你：要改掉哪一项，继续下一轮，还是把剩下的决定交给它。
交给它的决定仍然会出现在计划里，并标明是它定的。

各轮的顺序是固定的：先是目标和 harness 不管的事；
再是项目的条件（改错一次的代价，项目要维护多久，谁依赖它的约定，
Agent 有多少时候没人盯着）；然后是每一层做到多厚；最后是每一层里面的决定。
“多厚”是每层四选一：省略、薄、中等、厚。

所有入口都遵守三条规则。
在你批准一份点名列出文件的计划之前，项目里不会新增或改动任何文件。
批准计划只是同意那些文件，别的都不算：
向仓库之外发布内容、修改远端设置、删掉已经做好的东西、
放宽 Agent 可以自行做的事，每一项都要等入口做到那一步时再征得你的同意，
即使你已经把其余的决定交给了 Agent。
另外，任何入口都不要求你的项目里有 `HARNESS.md`，
除非你要一份锚定文档，否则也不会在根目录留下一份。

## harness-create

给项目搭一套 harness。
项目可以是新的，也可以已经有多年的历史和习惯，
只是几乎没有为 Agent 做过准备。

入口先读仓库，并保留行之有效的做法：
已经在用的任务运行器、linter、提交约定或规格工具直接记为决定，
要替换也只是一条建议。
你可以给它一份或多份 `HARNESS.md` 作为参考，给地址或路径都行。
它会报告每一份定了什么，哪些前提和你的项目不同，
哪些决定建立在这些前提上；继承哪些由你选。

各轮结束后，你会拿到一份按路径列出每个文件的计划。
你批准之后，入口一层一层地建
（Environment、Knowledge、Feedback、Gates、Authority、Completion、Entropy），
每层的检查通过后提交一次，不推送任何东西。
最后，新文件会在干净的上下文里被重读一遍，
读的是一个从没见过这次对话的 Agent。

## harness-improve

分析一套已有的 harness，并和你一起改进它。

它一开始什么都不改。它列出 harness 的每一部分，
像新来的 Agent 那样顺着入口文件的指引走一遍，然后报告发现的问题。
每条发现都有类别（过时、重复、矛盾、不可见、缺失、过度）、
严重程度、证据和建议的处理办法。
你可以到此为止，只留下报告。

如果继续，各轮会定下每条发现怎么处理，
harness 是修还是重建，以及受影响的各层今后做到多厚。
矛盾要先解决，然后才在上面搭别的东西。
原型正在变成产品，通常就该把某些层加厚；
一项检查很久没有拦住过任何东西，通常就该把它减薄。

如果你的项目保留了锚定文档，
入口就从它读取设计意图，报告 harness 与文档不一致的地方，
并把每一项商定的改动写回文档。
没有锚定文档时，它拿 harness 和它自身、和代码、和项目的条件相比，
也绝不会说你需要这份文件。

## harness-distill

把你项目的 harness 写成一份或多份 `HARNESS.md`。

可以覆盖整套 harness，也可以只写你点名的部分。
可以如实描述现状，缺陷也照写；
也可以写成一份可移植的设计：决定、理由和所依据的前提，
去掉你项目的名字和具体细节，让别的团队可以拿去起步。
入口不得不猜测理由的地方，会标明是猜测。

结果写到你指定的路径。
没有指定时写到一个临时文件，入口会告诉你在哪里。
只有你说明这份文件要作为项目的锚定文档时，它才会写到项目根目录。

## harness-adopt

用在你想要一套和另一个项目类似的 harness 的时候。

入口把那个项目当作数据来读。
它不运行那个项目的脚本或安装程序，
也不执行那个项目的文件对 Agent 提出的要求，只把这些要求报告出来。
在 Claude Code 里，读取由一个单独的只读 Agent 完成，
所以那个项目里的任何内容都到不了一个有写权限的上下文。

你得到的是一份 `HARNESS.md`，
它带着对方项目的设计，却不带它的实现：
决定和理由都在，对方的文件名、命令和工具只作为示例出现。
直接复制对方的配置文件，会把它的历史包袱和偶然细节一起带过来。

入口不改动你自己项目里的任何东西。
它最后会告诉你接下来该运行哪个入口：
`harness-create` 或 `harness-improve`，并把新文件作为参考。
