# Reclamation

Read when the project is maintained for years
and nothing cleans the harness periodically,
or when the user asks how to keep the repaired harness from decaying again.
Sync at edit time catches drift as files change;
a periodic clean-up catches what nobody edited.
Installing the routine belongs to the Entropy layer;
this file is what the decision and the plan item ask of it.

## What each run hunts

- Stale paths and dead commands: run them, do not trust them.
- Rules the code now contradicts, and specs that drifted.
- One rule stated in two places.
- Content no entrypoint route reaches; triggers that can no longer fire.
- Constraints that no longer catch anything, each with its evidence.
- Open items recorded where the project collects harness deviations.

Every item found is fixed in the same run or recorded as a tracked item.
Deleting stale content is the goal, not a loss.

## Cadence

Choose by how fast the project changes:
monthly when it moves fast, quarterly otherwise.
Tie it to an event the team already has (a release, a retrospective)
so the routine has a trigger,
and record the date of the last run as an absolute date.

## Recommendation

Put it to the user as one decision with two options:

- a short dated section in a knowledge file
  (the hunt list, the cadence, the event, the last run):
  recommended when Entropy is confirmed as medium;
- a clean-up project skill:
  recommended only when Entropy is confirmed as thick
  or the hunt has steps specific to the project.

With Entropy omitted or light, propose no routine;
say in the closing report that nothing catches what nobody edits.
